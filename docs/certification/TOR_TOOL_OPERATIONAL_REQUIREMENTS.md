## 5. Conditions of use the user must respect

1. Build with the binaries whose hashes are in the evidence file; rebuild and requalify after any change of the compiler sources.
2. Treat a `rejected` or `unsupported` verdict of `ltv` as: this function's object code is not covered by translation validation.
3. Release critical outputs through `lsafety_envelope`; a `SAFE_STATE_TRIP` is not to be overridden by retry.
4. Keep run-time contract checks enabled; an obligation reported as `runtime_checked` is not proven.
5. Code that must be constant time at machine level is written as constant-time kernels (`@secret` + `@no_alloc`) and passed through `ltv`: a plain `@secret` function that reaches a runtime helper is rejected ([C0010] is closed over calls), and the property is about the instruction text, not about the micro-architecture.
6. Use the stack bound of `lstack` together with the [E0210] acceptance of the same source: the bound is exact for the emitted text on the paths that remain under those range proofs, and trap paths and signal frames are outside it.
7. Give every tool of the chain the artifact the previous tool produced (the certified source, the `.s` the build left, the certificate directory `ltv` wrote) and compare the SHA-256 each report states; `tests/harness/synergy_gate.src` is the reference chain.
8. Verify a received evidence package with `@verify`; the signing certificate is self-signed, so trust in the key has to come from outside the package (for example the key recorded in the repository).
