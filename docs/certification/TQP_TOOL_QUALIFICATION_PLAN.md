## 5. Known limits of the evidence

1. `ltv` covers the integer fragment (int/bool parameters, + - * / %, comparisons, and/or, if, let, calls, ctfail, and the constant-time kernels). Functions outside it are reported `unsupported`, never `validated`. `ltv` validates the lowering its linked front end produces; for code built with `--critical` it must be started with that flag too (the synergy gate does), and it has no documented option for it.
2. `ltv` reasons over the integers: its theorem holds for executions without an i64 overflow trap. Constant-time kernels (`@secret` + `@no_alloc`) are the exception: `ltv` re-derives every range and their theorem has no overflow proviso; its hypothesis is that every argument is an immediate integer, which the entry guard of the kernel enforces by faulting.
3. The integer runtime helpers (mkint, addv, __rt_sub, __rt_mul, __rt_div, __rt_mod, the wrapping variants, cmpv, eqv, __rt_uint, __rt_un2, __rt_ustk, __rt_cond, __rt_qnext, __rt_idiv, __rt_imod) are no longer unverified axioms: `ltv_rt` verifies the emitted code of each against its specification for all inputs of the modelled cases (gate G-TVRT, probes P-TVRT-*, the synergy gate). In this run every `ltv` report of the certified modules carries `runtime_helpers_verified`: the helpers of the validated text were verified in the same run. What remains assumed: the x86-64 machine model of `ltv_rt` (items X1..X9 of ltv_rt.src), the allocator and the collector behind a boxed result (only the register writes of the allocator fast path are checked), the trap tail `__rt_die3`, and every helper that is not an integer helper (strings, lists, records, I/O): those are tested and stressed, not verified.
4. The Lean 4 certificates are exported but were not machine-checked unless the evidence file says `lean_checked: true`. The SMT-LIB2 certificates are checked by `lsmt`, a native decision procedure that shares no code with `ltv` (gate G-SMT, probes P-SMT-*, the synergy gate). In this run every `ltv` report of the certified modules carries `smt2_checked_native`: each exported certificate was checked natively in the same run. An external solver (z3) checks them only when it is installed; the `gates` section records `external_solver_ran` for G-SMT. `unsat` establishes that the certificate text is a valid refutation; that its terms describe the source and the emitted assembly is the binding `ltv` makes. `lsmt` was written by the same team as `ltv`.
5. `lmcdc` measures coverage of the lowered AST the code generator receives. All four certified modules must have 0 uncovered obligations or the qualification fails. A witness is confirmed by the value, or the contract trap, the real binary produces for it. In this run `ltv` reports `branch_correlation` for the certified modules (`uncorrelated` must be 0): each decision of the lowered AST is matched with a conditional jump of the validated object code. The witnesses come from the tool's own search over the literals of each function, not from the `test_*` functions of the module. It analyzes the typed int/bool functions that do not call themselves (`typed_integer_functions_in_source` against `functions` in the evidence). The false outcome of the conclusion of a declared law is not exercised: it is unreachable exactly when the law holds, which rests on the proof status of that law.
6. Channel B of the safety envelope is produced by a clean-room front end and RV32IM code generator inside lsafety_envelope.src; its tool links no compiler module (gate G-ENV and probe P-ENVX-POS-INDEP scan the bundle), so the lumec front end is no longer a common mode of the two channels. Common modes that remain: both channels are given the same kernel text and the same language definition (a wrong specification is implemented twice); the same team wrote both front ends; in lockstep mode both run on one host, one operating system and one clock; the voter and the event log are single; the monitor is a software RV32IM interpreter and, in the split bundle, QEMU: emulators, not silicon, and two processes on one host, not two boards. Its number domain is i32.
7. The stack bound of `lstack` is computed on the emitted text and is exact for that text on the paths that remain under the [E0210] range proofs (the report lists every slow-path edge it removed and why); over all syntactic paths the bound is unbounded whenever a slow path can box. Trap paths and asynchronous signal frames are outside the model. The latency jitter of gate G-REALTIME is a measurement on this host, not a worst-case execution time.
8. The runtime beyond the verified integer helpers (collector, boxed values, string and list primitives) and `lasm` are tested and stressed, not formally verified.
9. QUALIFICATION_EVIDENCE.json is hash-chained and signed with Ed25519 with a developer key that this tool generates and keeps in a file on the host: no hardware (HSM, TPM) protects it. QUALIFICATION_SIGNING_CERT.der is a SELF-SIGNED X.509 v3 certificate for that key, validated against itself as trust anchor: it states subject, validity and usage and binds the key to no identity; no authority issued it. A new key is generated only when the OS entropy health check passes; that check detects a dead, stuck or repeating source and does not measure or certify entropy. The signature shows which key holder produced the file; it is not an attestation by an independent party. The summary files of the gates are covered through their SHA-256 in the `gates` section; the soak ledger and the safety-envelope event log are hash-chained, not signed.
10. The AArch64, RV64 and RV32 back ends cover the integer kernel fragment only and were executed on emulators (qemu user mode, qemu-system-riscv32, the LumePuter interpreter), not on silicon.
11. [C0010] is closed over calls: the instructions of every routine a `@secret` function reaches by call or jmp, user functions and runtime text alike, are scanned, and a plain `@secret` function that calls a runtime helper is rejected. It is a property of the instruction text (no secret-dependent conditional branch, no division, no memory access outside the frame). It says nothing about the micro-architecture: caches, speculation, or instructions whose latency depends on their operands on a given CPU. The dudect test of the cryptography gate is a statistical timing test on this host.
12. The cryptography of `lcrypto_tls.src` is tested against the official vectors and against forgeries; it is not formally verified. Its primitives that are written as constant-time kernels (`lct_k_*`) are under the machine-level check of item 11; the rest is constant-time by construction at source level only. X.509 path validation exists for Ed25519 chains with pinned trust anchors: no RSA / ECDSA, no name constraints, no host name or subjectAltName matching, no revocation (CRL, OCSP). TLS 1.3 is one cipher suite and one group, without PSK, 0-RTT, HelloRetryRequest, client certificates or KeyUpdate. The entropy health check is described in item 9.
13. A neural cartridge is evaluated by the integer forward pass of this tool chain; nothing is claimed about a floating-point inference engine that loads the same file.
14. `lcert --check-source` binds the fragment its own reader understands (integer functions, laws, `@bound`, direct recursion with a measure, the two SIMD intrinsics); a contract over bit operations is reported unbound, so a constant-time kernel carries no certified `ensures`.
